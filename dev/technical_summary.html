1. Background — what the original package did

The original detectRUNS (pre-2.0) exposed two top-level functions: slidingRUNS.run() and consecutiveRUNS.run(). Both accepted a PED/MAP file pair and returned a plain data.frame of runs.

How the original PED path worked

  • Read the entire PED file into R memory as a character matrix (one row per individual, all SNP alleles as strings).
  • For each individual, call an inner R loop (or a thin C++ helper snpInRunCpp) to evaluate each SNP.
  • The outer loop — iterating over individuals and chromosomes — was pure R, which meant function call overhead for every SNP of every individual.
  • All intermediate data lived in R-level objects, held in memory for the entire scan duration.

Problems that motivated the redesign

2. Phase 1 — C++ BED engine & ROH S3 class NEW

Commit: dfdc5c7 — "detectRUNS 1.0.0 — C++ BED engine, ROH S3 class, CRAN cleanup"

2.1 New entry point: scanRUNS()

A single new function replaces both slidingRUNS.run() and consecutiveRUNS.run(). It accepts either a BED file path (new fast path) or a PED file path (legacy path, unchanged). 

scan <- scanRUNS("dataset.bed",
                  method        = "sliding",   # or "consecutive"
                  ROHet         = FALSE,        # ROHom (default) or ROHet
                  minSNP        = 15,
                  maxOpp        = 1,
                  maxMiss       = 1,
                  minLengthBps  = 1e6,
                  maxGap        = 1e6,
                  windowSize    = 15,           # sliding only
                  threshold     = 0.05,         # sliding only
                  nThreads      = 14)           # OpenMP threads

2.2 The C++ BED engine

PLINK BED files store genotypes as SNP-major binary: one row per SNP, all N individuals packed 4-per-byte at 2 bits each. The new engine reads BED natively in C++:

  • bed_reader.cpp — opens the BED file with mmap() (memory-mapped I/O). The file is never copied into R memory; the OS maps it directly into the process address space. Random access is O(1).
  • scan_roh.cpp — implements both the sliding-window and consecutive state machines entirely in C++. No R-level loop overhead.
  • rcpp_entry.cpp — thin Rcpp bridge that marshals R arguments in and the result data.frame out.
Why mmap instead of fread?
fread would copy the entire file into a new allocation. mmap lets the kernel page-in only the bytes actually accessed, and avoids doubling memory usage for large files. For Innovagen_HD (777K SNPs × 1009 individuals ≈ 196 MB BED), this matters.

scanRUNS() now returns a ROH S3 object instead of a plain data.frame. This object carries everything downstream functions need:

3. Phase 2 — Correctness audit & PLINK compatibility FIX

Commits: f1a2915, 7f23d4a, cd6788f, e31bff7, 7938e1a, 2351373

After the C++ engine landed, a systematic comparison against PLINK --homozyg revealed several semantic mismatches. Each was fixed independently so the cause was clear.

3.1 PLINK-compatible sliding-window threshold

PLINK uses ≥ threshold (inclusive) to declare a window "passing". The original code used > threshold (exclusive), causing a small fraction of windows to be wrongly excluded when the fraction of homozygous SNPs exactly equalled the threshold. 

// Fixed: >= matches PLINK --homozyg
const bool in_roh = (static_cast<float>(h) / n_cov >= static_cast<float>(p.threshold));

3.2 Run-level maxGap split

The original PED path applied the gap check at window level (closing the current window), not at run level. PLINK splits an open run when any two consecutive in-ROH SNPs are further apart than maxGap. This was fixed by tracking run_end_bp and checking the gap before extending the run.

3.3 Inclusive run length

Run length was computed as end_bp − start_bp (exclusive), giving lengths 1 bp short. PLINK uses end_bp − start_bp + 1 (inclusive). Fixed across all code paths (C++ and R).

3.4 Chromosome-boundary gap bug (PED path)

The legacy R path reused last_bp across chromosome boundaries, so the first SNP of each new chromosome incorrectly triggered a gap check against the last SNP of the previous chromosome. Fixed by resetting last_bp on every chromosome transition.

4. Phase 3 — New features NEW

4.1 runsIslands() — permutation-based ROH island detection

Commits: 8027de0, 32935d4, 7a867a2, 7ad6f45

Implements the Falchi et al. approach for detecting genomic regions where ROH accumulate above chance (called "ROH islands" or "islands of homozygosity").

Algorithm:

  1. For each chromosome independently, compute the observed SNP-ROH frequency vector (how many individuals have a ROH covering each SNP).
  2. Run n_perm permutations: randomly shuffle individual-level ROH assignments and recompute the frequency vector.
  3. The per-SNP threshold is the percentile-th quantile of the permutation distribution at that SNP.
  4. SNPs where the observed frequency exceeds the threshold are declared "island SNPs".

The permutation loop is in perm_roh.cpp, parallelised over permutations with OpenMP (#pragma omp parallel for over n_perm). Each permutation is independent, so this scales near-linearly with threads.

Key optimisation in perm_roh.cpp: The chromosome genotype matrix (int8_t[n_c × N]) is decoded once before the permutation loop and passed as a raw pointer into each permutation. This avoids calling decode_snp_row() inside the hot loop — a significant saving when running 100+ permutations.

Returns a ROHIslands S3 object with print(), summary(), and plot() methods.

4.2 runsAssociation()

Commit: eda4c54

Tests for association between ROH presence/absence at each genomic position and a phenotype of interest (continuous or binary). Uses a permutation-based approach analogous to runsIslands.

4.3 reportRUNS() — automated HTML/Markdown/PDF report

Commits: 1fccaec, 9b0afa0, 31915ed

Generates a self-contained report from a ROH object covering:

  • Scan provenance (parameters, date, detectRUNS version)
  • Run count and length distributions by individual and by group
  • Froh inbreeding coefficients (genome-wide and per-chromosome)
  • SNP-in-ROH frequency Manhattan plot
  • ROH islands results (if computed)
  • Common RUNS regions summary table (group × chromosome)

5. Phase 4 — Multi-threaded parallelism PERF

5.1 First attempt: chromosome-parallel scan

Commit: 20e1b98 — "Merge branch 'perf/omp-chromosome-parallel'"

The first OpenMP implementation parallelised the outer loop over chromosomes: each thread received a subset of chromosomes and processed all N individuals for those chromosomes. 

#pragma omp for schedule(dynamic, 1)
for (int c = 0; c < n_chrom; ++c) {   // ~30 work units
    // decode row by row, update all N individuals' state machines
}
Why this did not scale: A typical livestock genome has ~30 autosomes. With 14 threads and only 30 work units, many threads sit idle for much of the scan — particularly with schedule(dynamic), where later threads wait for the last few long chromosomes to finish. Benchmarks confirmed: no measurable speedup at 10 or 14 threads vs 1 thread for scanRUNS().

5.2 Individual-parallel scan (current implementation)

Commit: 4e43dec — "perf: individual-parallel scan for SNP-major BED in scanRUNS()"

The redesign switches the parallelism axis from chromosomes to individuals. With N = 1,009–4,653 individuals, there are orders of magnitude more work units than threads.

How SNP-major BED enables per-individual access without extra memory

In a SNP-major BED, individual i's genotype at SNP j lives at a predictable byte offset: 

// byte containing individual i at SNP j:
bed.data[3 + j * row_bytes + i/4]
// two-bit genotype at bits (i%4)*2 .. (i%4)*2+1

The function decode_individual_snp_major() walks the mmap at stride row_bytes (one step per SNP), extracting all M genotypes for individual i into a thread-local int8_t[M] buffer. No copy of the BED file, no matrix transpose — just strided reads through the existing mmap. 

static void decode_individual_snp_major(
    const BedFile& bed, int ind_idx, int M, int8_t* out)
{
    const int      byte_off = ind_idx / 4;
    const int      bit_sh   = (ind_idx % 4) * 2;
    const uint8_t* base     = bed.data + 3;
    for (int j = 0; j < M; ++j) {
        const uint8_t b = base[(size_t)j * bed.row_bytes + byte_off];
        out[j] = BED_BITS_TO_GENO[(b >> bit_sh) & 0x03];
    }
}

Thread structure

#pragma omp parallel num_threads(actual)
{
    const int tid = omp_get_thread_num();
    std::vector<int8_t> ind_buf(M);          // M bytes per thread, ~778 KB max

    #pragma omp for schedule(static)
    for (int i = 0; i < N; ++i) {           // N = 1009–4653 work units
        decode_individual_snp_major(bed, i, M, ind_buf.data());
        // run consecutive or sliding state machine for individual i
        // writes to summaries[i] (no race: each thread owns disjoint i)
        // writes to tl_rec[tid], tl_freq[tid] (thread-local)
    }
}
// merge tl_rec[t] and tl_freq[t] after parallel section

Memory overhead

The only extra allocation is n_threads × M bytes scratch buffers. For Innovagen_HD (M = 777,962) at 14 threads: 14 × 778 KB ≈ 11 MB. No copy of the BED file, no NxM genotype matrix.

6. Phase 5 — Bug fixes & minor improvements FIX

6.1 Froh_inbreeding() returning NA for zero-run individuals

Root cause: Froh_inbreeding() builds the Froh data.frame with tapply() over the runs data. Individuals present in sample_info but absent from the runs data.frame (because they have zero ROH) never appear in the tapply result. An outer join merge(info_breed, Froh, by="id", all=TRUE) correctly includes them but leaves their Froh columns as NA.

Fix: Zero-fill all Froh columns after the merge:

Froh <- merge(info_breed, Froh, by = "id", all = TRUE)
if (genome_wide) {
    Froh$sum[is.na(Froh$sum)]                 <- 0
    Froh$Froh_genome[is.na(Froh$Froh_genome)] <- 0
} else {
    for (col in setdiff(names(Froh), c("id","group")))
        Froh[[col]][is.na(Froh[[col]])] <- 0
}

6.2 OOM crash in tableRuns() on large datasets

tableRuns() used parallel::mclapply() (fork-based parallelism on Unix) to compute per-chromosome common-region tables. For datasets with many individuals and many runs, forking the R process duplicated the entire heap — triggering OOM kills.

Fix: Replaced mclapply() with lapply(). The per-chromosome computation is fast enough sequentially; the memory cost of forking was not justified.

6.3 perm_roh.cpp — pre-decode chromosome genotypes

Previously, scan_chrom_consec_perm() and scan_chrom_sliding_perm() called decode_snp_row() inside the per-permutation loop — decoding the same rows 100+ times. Refactored to decode the chromosome genotype matrix once (int8_t[n_c × N]) before the permutation loop and pass a raw pointer in.

6.4 reportRUNS() — common regions section

The common-regions table previously listed every individual run region verbatim (potentially thousands of rows). Replaced with a per-group × chromosome summary showing N_regions, Total_Mbp, Mean_nSNP, and the top region.

6.5 Validation infrastructure

Per-scan subprocess isolation: the full validation suite now runs 64 independent R subprocesses (4 datasets × 2 run types × 2 methods × 4 param sets), each launched by run_all_sequential.sh via environment variables (DATASET_FILTER, TYPE_FILTER, METHOD_FILTER, PARAMS_FILTER). Each process exits cleanly before the next starts, preventing memory accumulation across scans.
